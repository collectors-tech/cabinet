## Visible Provider Sources

Cabinet no longer has a purely static Integrations provider card list. The `/integrations` route renders `Integrations`, which delegates to `Apps`, and `Apps` loads providers from `/api/providers/registry` before sorting, filtering, and opening provider setup dialogs.

Primary files:

- `ui.web/src/routes/_authenticated/integrations/index.tsx`
- `ui.web/src/features/integrations/index.tsx`
- `ui.web/src/features/apps/index.tsx`
- `internal/app/app.go`

## Hardcoded Provider Lists

Current hardcoded provider definitions and lists:

- `internal/app/app.go`: `providerRegistryPayload` defines base OpenAI, Telegram, eBay, Amazon entries and appends AU webshop domains.
- `internal/app/app.go`: `defaultAUWebshopDomains()` defines the default AU webshop catalog.
- `internal/app/app.go`: several provider run handlers still read provider-specific settings keys directly.
- `ui.web/src/features/apps/index.tsx`: `providerSettingsKeys()` mirrors backend settings key generation for the setup dialog.
- `ui.web/src/features/scanner/index.tsx`: `MARKET_WATCH_PROVIDER_OPTIONS` is a separate Market Watch provider selector; it must be reconciled with registry data during migration.
- `internal/scanner/providers.go`: scanner provider registry is a lightweight runtime factory map and returns a disabled provider for unknown providers.
- `internal/ai/providers.go`: AI provider registry exposes OpenAI plus disabled placeholder providers for Anthropic and Google.

Migration risk: the Integrations UI slugifies provider IDs with underscores while some existing run handlers use older dotted/hardcoded keys such as `integration.bonzaslotcars.base_url`. Registry migration should standardize key mapping or provide explicit aliases before moving provider setup fully into registry-driven forms.

## Backend/API Workflow Usage

Implemented provider/API surfaces found in `internal/app/app.go` and OpenAPI:

- `/api/providers/registry`: provider registry payload for Integrations UI.
- `/api/provider/health`: provider health/readiness for eBay and OpenAI; registry also maps scanner health for other provider IDs when available.
- `/api/provider/test`: provider connectivity/readiness test, currently meaningful for OpenAI API-key and Browser Auth proof paths.
- `/api/providers/ebay/run`: saved-search provider run for eBay, using active-profile eBay settings.
- `/api/providers/amazon/run`: disabled/program-API gated contract path.
- `/api/providers/bonza/run`: Bonza product/category search run.
- `/api/providers/bigcommerce/run`: BigCommerce/storefront run path.
- `/api/providers/frontline/run`: Frontline/Algolia discovery run path.
- `/api/providers/hobbytech/run`: Hobbytech/Boost search run path.
- `/api/providers/product-url/ingest`: provider URL ingest into inventory draft workflow, currently used by item creation UI.
- `/api/providers/family-detect` and `/api/providers/family-override`: provider API-family detection and override persistence.
- `/api/scanner/*`: Market Watch query sets, run history, candidates, failures, retries, and provider-scoped saved searches.
- `/api/integrations/ebay/purchase-inbox/*`: eBay purchase capture/reconciliation review and actions.
- `/api/telegram/catalog-captures`, `/api/telegram/catalog-capture-callbacks`, `/api/telegram/external-intake-proofs`, `/api/telegram/webhook/catalog-captures`: Telegram governed capture and external proof workflows.

Assistant/chat usage:

- `internal/app/assistant_capabilities.go` defines `integrations.provider.run` as setup-needed until provider credentials and health are verified.
- Chat UI defaults read `assistant_default_provider` and `assistant_default_model`, defaulting to OpenAI when unset.
- OpenAI provider behavior is implemented in `internal/ai` and OpenAI config/readiness handlers in `internal/app/app.go`.

## Settings And Secrets Paths

Current persistence model:

- Profile settings API: `/api/profiles/{profileID}/settings`.
- Profile secrets API: `/api/profiles/{profileID}/secrets`.
- OpenAI API key: secret `openai_api_key`; non-secret OpenAI method/model/defaults in profile settings.
- OpenAI Browser Auth readiness: profile settings such as `openai.active_auth_method`, `openai.browser_auth_state`, `openai.browser_auth_artifact_present`, `openai.browser_auth_provider_test_state`, and proof artifact/message fields.
- Telegram capture authorization: profile settings `telegram.catalog_capture.sender_id` and `telegram.catalog_capture.chat_id`.
- eBay official API setup: profile settings `ebay_bearer_token`, `ebay_marketplace`, `ebay_base_url`, `integration.ebay.items_per_page`.
- AU webshop domain catalog: profile setting `integration.au_webshops.domains`.
- AU webshop setup keys: registry UI derives `integration.<slug>.base_url`, `integration.<slug>.token`, `integration.<slug>.marketplace`, `integration.<slug>.enabled`, and `integration.<slug>.items_per_page`.

Risk: eBay bearer token remains in profile settings rather than profile secrets, while OpenAI uses the secrets path. The registry spec expects secret values to be write-only and not returned from registry payloads, so eBay and optional BigCommerce/webshop token handling should be reviewed during registry migration.

## Migration Gaps And Risks

1. Provider settings-key normalization is split between backend and frontend, and some concrete run handlers still use older hardcoded keys. Migrate to one registry-owned settings-key contract or explicit alias map.
2. eBay token handling is settings-backed while OpenAI secret handling is secrets-backed. Decide whether eBay and optional webshop tokens must move to profile secrets before claiming registry secret consistency.
3. Market Watch provider options are still a separate UI list. It should source registry providers/capabilities or a dedicated query-provider registry projection.
4. AU webshop providers are all visible as ready, even when several are only default web-ingestion placeholders pending platform-specific probes.
5. Amazon is visible in the registry with a disabled/program-API gate but has only a disabled contract path unless `amazonMode` enables program API.
6. Assistant provider registry and app provider registry are separate. OpenAI is bridged in settings and health, but Anthropic/Google placeholders exist only in `internal/ai` and are not visible as full registry entries.
7. Telegram is represented as a provider in Integrations and as profile settings in Profile. Migration should keep a single source for sender/chat readiness while preserving the governed preview/apply workflow.
8. Provider family overrides can alter the registry payload, but run-handler routing is still endpoint-specific. The migration should define how an overridden family selects the execution adapter.
